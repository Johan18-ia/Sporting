Módulo de Autenticación y Usuarios (MOD_01)
HU01: Iniciar Sesión
Estado: Implementada
Contexto: Como usuario registrado, quiero ingresar mi correo y contraseña para acceder al sistema y continuar con mi sesión de forma segura.

Criterios de Aceptación:

Escenario Principal (Happy Path):

Dado que un usuario está registrado en la tabla users y su cuenta está activa (is_active = 1).

Cuando ingresa su email y contraseña correctos en la pantalla de Login y presiona "Iniciar Sesión".

Entonces el sistema autentica las credenciales, guarda el token JWT en almacenamiento local (AsyncStorage) y redirige al usuario al panel principal correspondiente (MainTabs con Dashboard o Students según rol).

Escenario de Validación de Campos (Campos Requeridos):

Dado que el usuario no ha ingresado un valor en el campo de "Correo Electrónico" o "Contraseña".

Cuando presiona "Iniciar Sesión".

Entonces el sistema muestra un mensaje de validación: "Por favor complete todos los campos".

Escenario de Datos Inválidos (Partición de Equivalencia - Correo):

Dado que el usuario ingresa un email con un formato incorrecto (ej. "usuario@.com", "usuario.com", "@dominio.com").

Cuando presiona "Iniciar Sesión".

Entonces el sistema muestra un mensaje de error: "Por favor ingrese un correo electrónico válido".

Escenario de Credenciales Incorrectas:

Dado que el usuario ingresa una contraseña que no coincide con el registro en la base de datos.

Cuando presiona "Iniciar Sesión".

Entonces el sistema muestra un mensaje de error genérico: "Contraseña o correo incorrecto".

Escenario de Usuario Inactivo:

Dado que el usuario está registrado pero su cuenta está desactivada (is_active = 0).

Cuando ingresa sus credenciales correctas y presiona "Iniciar Sesión".

Entonces el sistema muestra un mensaje de error: "Usuario desactivado. Contacte al administrador".

Escenario de Redirección por Rol:

Dado que el usuario autenticado tiene rol admin o seller.

Cuando el login es exitoso.

Entonces el sistema redirige al usuario a la pantalla Dashboard.

Dado que el usuario autenticado tiene rol user (estudiante).

Cuando el login es exitoso.

Entonces el sistema redirige al usuario a la pantalla Students.

Escenario de Rendimiento:

Entonces la respuesta del sistema (login exitoso o fallido) debe ser menor a 2 segundos.

HU02: Cerrar Sesión
Estado: Implementada
Contexto: Como usuario autenticado, quiero cerrar mi sesión para finalizar el acceso de forma segura.

Criterios de Aceptación:

Escenario Principal:

Dado que el usuario ha iniciado sesión correctamente.

Cuando el usuario accede al perfil o menú de configuración y selecciona la opción "Cerrar Sesión".

Entonces el sistema muestra un cuadro de confirmación preguntando si desea cerrar la sesión.

Escenario de Confirmación y Cierre:

Dado que el usuario confirma la acción de cerrar sesión.

Entonces el sistema limpia el token JWT, la información del usuario y el token expiry del almacenamiento local (auth_token, auth_token_expiry, user_data).

Entonces el sistema redirige al usuario a la pantalla de autenticación (Home).

Entonces el usuario no debe poder continuar navegando en rutas protegidas sin volver a autenticarse.

Escenario de Cancelación:

Dado que el usuario selecciona "Cancelar" en el cuadro de confirmación.

Entonces el sistema mantiene la sesión activa y el usuario permanece en la pantalla actual.

HU03: Recuperar Contraseña
Estado: No implementada (flujo informativo)
Contexto: Como usuario, quiero recuperar el acceso a mi cuenta en caso de olvidar mi contraseña.

Criterios de Aceptación:

Escenario de Caso de Uso No Implementado:

Dado que el usuario está en la pantalla de inicio de sesión.

Cuando hace clic en "¿Olvidaste tu contraseña?".

Entonces el sistema muestra un mensaje informativo mediante Alert.alert: "Recuperar contraseña", "Para restablecer tu contraseña, comunícate con el administrador del sistema."

Escenario de Flujo Real No Implementado:

Dado que el usuario hace clic en "¿Olvidaste tu contraseña?".

Entonces el sistema no debe simular un flujo real de recuperación (no debe enviar correos, no debe mostrar formularios de restablecimiento, ni generar enlaces).

Entonces la única acción disponible es el mensaje informativo para contactar al administrador.

HU04: Autoregistro de Estudiante
Estado: Implementada
Contexto: Como estudiante o usuario nuevo, quiero registrarme en el sistema utilizando mis datos personales para poder acceder a la plataforma.

Criterios de Aceptación:

Escenario Principal (Happy Path):

Dado que el usuario accede a la pantalla de registro (RegisterScreen).

Cuando completa todos los campos obligatorios (Nombre, Apellido, Correo, Contraseña y Confirmación) con datos válidos y presiona "Registrarse".

Entonces el sistema crea un nuevo usuario con rol user, lo guarda en la base de datos y muestra un mensaje de éxito: "Registro exitoso", "Cuenta creada correctamente. Ahora puedes iniciar sesión."

Escenario de Validación de Campos:

Dado que el usuario deja un campo obligatorio en blanco (ej. 'Nombres', 'Correo Electrónico', 'Contraseña').

Cuando presiona "Registrarse".

Entonces el sistema muestra un mensaje de validación: "Por favor complete todos los campos obligatorios".

Escenario de Formato de Correo Inválido:

Dado que el usuario ingresa un correo con formato incorrecto (ej. "usuario@.com", "usuario.com").

Cuando presiona "Registrarse".

Entonces el sistema muestra un mensaje de validación: "Por favor ingrese un correo electrónico válido".

Escenario de Contraseña Segura (Valores Límite):

Dado que el usuario ingresa una contraseña con menos de 6 caracteres.

Cuando presiona "Registrarse".

Entonces el sistema muestra un mensaje de validación: "La contraseña debe tener al menos 6 caracteres".

Escenario de Confirmación de Contraseña:

Dado que el usuario ingresa una "Contraseña" y una "Confirmar Contraseña" que no coinciden.

Cuando presiona "Registrarse".

Entonces el sistema muestra un mensaje de validación: "Las contraseñas no coinciden".

Escenario de Correo Duplicado:

Dado que el usuario intenta registrarse con un correo que ya está registrado en la base de datos.

Cuando presiona "Registrarse".

Entonces el sistema muestra un mensaje de error: "El correo electrónico ya está registrado".

HU05: Registrar Usuario (Admin/Seller)
Estado: Implementada
Contexto: Como administrador o seller, quiero registrar nuevos usuarios para administrarlos dentro del sistema.

Criterios de Aceptación:

Escenario Principal (Happy Path):

Dado que un administrador ha iniciado sesión.

Cuando accede al formulario de usuario (UserFormScreen), completa los campos (Nombre, Apellido, Correo, Contraseña, Teléfono, Rol) y presiona "Crear Usuario".

Entonces el sistema crea el usuario, lo guarda en la base de datos y muestra un mensaje de éxito: "Usuario creado correctamente".

Escenario de Validación de Campos Requeridos:

Dado que el administrador deja el campo "Nombre" en blanco.

Cuando presiona "Crear Usuario".

Entonces el sistema debe mostrar un mensaje de validación: "El nombre es requerido".

Escenario de Rol y Categoría:

Dado que el administrador selecciona el rol "Administrador" o "Vendedor" ("seller").

Cuando presiona "Crear Usuario".

Entonces el sistema debe ocultar el campo de "Categoría" (ya que estos roles no pertenecen a una categoría) y guardar el usuario sin una category_id.

Escenario de Datos Inválidos (Partición de Equivalencia - Correo):

Dado que el administrador ingresa un email con formato inválido.

Cuando presiona "Crear Usuario".

Entonces el sistema muestra un mensaje de validación: "Email inválido".

Escenario de Rol "Usuario" con Categoría:

Dado que el administrador selecciona el rol "Usuario" y no asigna una categoría.

Cuando presiona "Crear Usuario".

Entonces el sistema debe permitir la creación del usuario con category_id nulo.

Escenario de Correo Duplicado:

Dado que el administrador ingresa un correo que ya está registrado.

Cuando presiona "Crear Usuario".

Entonces el sistema muestra un mensaje de error: "El email ya está registrado".

HU06: Listar Usuarios
Estado: Implementada
Contexto: Como administrador o seller, quiero ver la lista de usuarios registrados para gestionarlos.

Criterios de Aceptación:

Escenario Principal:

Dado que un administrador ha iniciado sesión.

Cuando accede a la sección "Usuarios" (UsersScreen).

Entonces el sistema muestra una lista de todos los usuarios registrados, mostrando al menos: Nombre, Correo, Rol y Estado (Activo/Inactivo).

Escenario de Ordenamiento por Rol:

Dado que el administrador está en la lista de usuarios.

Entonces los usuarios deben aparecer ordenados por prioridad: admin → seller → user.

Entonces los usuarios del mismo rol se ordenan alfabéticamente por nombre.

Escenario de Búsqueda:

Dado que el administrador está en la lista de usuarios.

Cuando ingresa un término de búsqueda (ej. "Juan") en el campo de "Buscar usuarios".

Entonces el sistema filtra la lista para mostrar solo los usuarios cuyo nombre, apellido o correo coincidan con el término ingresado.

Escenario de Filtro por Rol:

Dado que el administrador está en la lista de usuarios.

Cuando selecciona un filtro de rol (Admin, Seller, Usuario, Todos).

Entonces el sistema filtra la lista para mostrar solo los usuarios del rol seleccionado.

Escenario de Identificación del Usuario Autenticado:

Dado que el usuario autenticado aparece en la lista.

Entonces el sistema debe mostrar una etiqueta "Tú" junto al nombre del usuario autenticado.

Escenario de Identificación de Estudiante:

Dado que un usuario de rol user tiene un registro asociado en la tabla students.

Entonces el sistema debe mostrar una etiqueta "Estudiante" en lugar de "Usuario regular".

HU07: Obtener Usuario por Identificador
Estado: Implementada
Contexto: Como administrador o seller, quiero consultar el detalle completo de un usuario para revisarlo o gestionarlo.

Criterios de Aceptación:

Escenario Principal:

Dado que el administrador está en la lista de usuarios.

Cuando toca un usuario específico.

Entonces el sistema navega a la vista de detalle (UserDetailScreen) que muestra la información completa del usuario: Nombre, Apellido, Correo, Teléfono, Rol, Estado (Activo/Inactivo), Categoría (si aplica) y Fecha de Registro.

Escenario de Acceso Rápido a Edición:

Dado que el administrador está en la vista de detalle de un usuario.

Entonces el sistema muestra un botón "Editar" que permite navegar al formulario de edición (UserFormScreen).

Escenario de Acceso Rápido a Cambio de Estado:

Dado que el administrador está en la vista de detalle de un usuario.

Entonces el sistema muestra un botón para "Activar" o "Desactivar" según el estado actual del usuario.

Escenario de Usuario No Encontrado:

Dado que el administrador intenta acceder a un usuario con un ID que no existe en la base de datos.

Cuando la petición al backend (/api/users/:id) devuelve 404 o null.

Entonces el sistema muestra un mensaje de error: "Usuario no encontrado" y redirige a la lista de usuarios.

HU08: Editar Usuario
Estado: Implementada
Contexto: Como administrador o seller, quiero actualizar la información de un usuario para mantener sus datos al día.

Criterios de Aceptación:

Escenario Principal (Happy Path):

Dado que un administrador está en la vista de detalle de un usuario.

Cuando hace clic en "Editar", modifica el campo "Nombres" y presiona "Actualizar Usuario".

Entonces el sistema guarda los cambios en la base de datos y muestra un mensaje de éxito: "Usuario actualizado correctamente".

Escenario de Validación de Campos:

Dado que el administrador intenta actualizar el campo "Nombres" con un valor vacío.

Cuando presiona "Actualizar Usuario".

Entonces el sistema muestra un mensaje de validación: "El nombre es requerido".

Escenario de Cambio de Rol (Restricción):

Dado que el administrador intenta cambiar el rol de un usuario.

Cuando presiona "Actualizar Usuario".

Entonces el sistema permite el cambio de rol siempre que el usuario que realiza la edición sea administrador.

Escenario de Cambio de Rol (No Administrador):

Dado que un usuario con rol seller (vendedor) intenta editar a otro usuario.

Cuando presiona "Actualizar Usuario".

Entonces el sistema no debe permitir cambiar el rol del usuario editado (el campo de rol debe estar bloqueado o el rol no se envía en el payload).

Escenario de Edición del Propio Perfil:

Dado que un usuario está editando su propio perfil (el id del usuario editado coincide con el id del usuario autenticado).

Cuando presiona "Actualizar Usuario".

Entonces el sistema no debe enviar el campo role en el payload (para evitar que el usuario se auto-asigne un rol superior).

Entonces después de la actualización, el sistema debe refrescar la sesión local (checkAuth()) para reflejar los cambios en el contexto.

HU09: Cambiar Estado de Usuario (Activar/Desactivar)
Estado: Implementada
Contexto: Como administrador, quiero activar o desactivar usuarios para controlar su acceso al sistema.

Criterios de Aceptación:

Escenario Principal (Desactivar):

Dado que un administrador está en la vista de detalle de un usuario activo.

Cuando presiona el botón "Desactivar" y confirma la acción.

Entonces el sistema cambia el estado del usuario a is_active = 0 y muestra un mensaje de éxito: "Usuario desactivado correctamente". El usuario no podrá iniciar sesión.

Escenario Principal (Activar):

Dado que un administrador está en la vista de detalle de un usuario inactivo.

Cuando presiona el botón "Activar" y confirma la acción.

Entonces el sistema cambia el estado del usuario a is_active = 1 y muestra un mensaje de éxito: "Usuario activado correctamente". El usuario podrá iniciar sesión.

Escenario de Auto-Desactivación:

Dado que un administrador intenta desactivar su propia cuenta.

Cuando selecciona "Desactivar".

Entonces el sistema debe mostrar un mensaje de error: "Operación no permitida", "No puedes activar/desactivar tu propia cuenta desde aquí."

Escenario de Confirmación:

Dado que el administrador presiona "Desactivar" o "Activar".

Entonces el sistema debe mostrar un cuadro de diálogo de confirmación antes de proceder con el cambio de estado.

HU10: Eliminar Usuario
Estado: Implementada
Contexto: Como administrador, quiero eliminar un usuario cuando sea necesario y bajo confirmación.

Criterios de Aceptación:

Escenario Principal:

Dado que un administrador está en la lista de usuarios.

Cuando presiona el ícono de acciones (ellipsis-vertical) de un usuario y selecciona "Eliminar".

Entonces el sistema muestra un cuadro de diálogo de confirmación: "¿Estás seguro de eliminar a [nombre]?".

Escenario de Confirmación y Eliminación:

Dado que el administrador confirma la eliminación.

Entonces el sistema envía una solicitud DELETE al backend (/users/delete/:id) y, si es exitosa, remueve el usuario de la base de datos.

Entonces el sistema muestra un mensaje de éxito: "Usuario eliminado correctamente" y actualiza la lista de usuarios.

Escenario de Auto-Eliminación:

Dado que el administrador intenta eliminar su propia cuenta.

Cuando selecciona "Eliminar".

Entonces el sistema debe mostrar un mensaje de error: "Operación no permitida", "No puedes eliminar tu propia cuenta desde aquí."

Escenario de Cancelación:

Dado que el administrador presiona "Cancelar" en el cuadro de diálogo de confirmación.

Entonces el sistema no elimina al usuario y permanece en la lista de usuarios.

HU11: Editar Perfil
Estado: Parcialmente implementada
Contexto: Como usuario autenticado, quiero actualizar mi información personal para mantener mis datos actuales.

Criterios de Aceptación:

Escenario Principal (Happy Path):

Dado que un usuario autenticado está en su perfil (ProfileDetailScreen).

Cuando toca el botón "Editar" y modifica su número de teléfono en el formulario (UserFormScreen en modo edit).

Entonces el sistema actualiza la información del usuario en la base de datos y muestra un mensaje de éxito: "Usuario actualizado correctamente".

Entonces la sesión local se refresca (checkAuth()) y los cambios se reflejan en la vista de perfil.

Escenario de Campos Protegidos (Rol):

Dado que un usuario está editando su propio perfil.

Entonces el campo "Rol" debe ser de solo lectura (no editable por el usuario). El sistema debe mostrar el rol actual como texto sin opciones de selección.

Escenario de Modificación de Correo:

Dado que un usuario intenta cambiar su propio correo electrónico.

Cuando presiona "Actualizar Usuario".

Entonces el sistema permite la modificación del correo, siempre y cuando el nuevo correo no esté en uso por otro usuario.

Escenario de Contraseña (No Implementado):

Dado que un usuario está en el formulario de edición de perfil.

Entonces la sección de "Contraseña" no debe estar presente en el formulario general de edición de perfil.

Entonces la funcionalidad de cambio de contraseña no está implementada como un flujo independiente formalizado.

Escenario de Validación de Campos:

Dado que el usuario intenta actualizar el campo "Nombres" con un valor vacío.

Cuando presiona "Actualizar Usuario".

Entonces el sistema muestra un mensaje de validación: "El nombre es requerido".

Módulo de Reportes (MOD_06)
HU01: Generar Reporte de Estudiantes
Estado: No especificada en el documento de adaptación (se infiere implementada en ReportsScreen)
Contexto: Como administrador, quiero generar un reporte (CSV) con la lista de estudiantes filtrados por categoría.

Criterios de Aceptación:

Escenario Principal (Happy Path - Sin Filtro):

Dado que un administrador ha iniciado sesión correctamente.

Cuando accede a la sección de "Reportes" y selecciona la opción "Estudiantes".

Entonces el sistema realiza una solicitud GET al endpoint /api/students y genera un archivo en formato CSV que contiene todos los estudiantes registrados en el sistema.

Escenario de Estructura del Reporte (Contenido):

Dado que el administrador ha generado el reporte de estudiantes.

Entonces el archivo CSV debe contener las siguientes columnas: ID, Nombre, Apellido, Documento, Categoría, Teléfono.

Escenario de Datos Vacíos (Sin Estudiantes):

Dado que no hay estudiantes registrados en el sistema.

Cuando el administrador intenta generar el reporte.

Entonces el sistema debe mostrar un mensaje informativo: "Sin Datos", "No hay datos disponibles para Estudiantes".

Escenario de "Compartir" (Funcionalidad Móvil):

Dado que el reporte CSV ha sido generado exitosamente.

Entonces el sistema debe abrir el diálogo nativo de "Compartir" del dispositivo móvil (usando la API Share.share de React Native) para que el usuario pueda enviar el archivo por correo electrónico, WhatsApp, etc.

Escenario de Error en la Generación:

Dado que ocurre un error al obtener los datos del endpoint /api/students (ej. error de red, timeout, 500).

Cuando el administrador intenta generar el reporte.

Entonces el sistema debe mostrar un mensaje de error: "Error", "No se pudo generar el reporte".
